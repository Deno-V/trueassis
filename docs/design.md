# 体系设计（Design）

## 1. 为什么需要它

要做的事太多、跨领域（生活/工作/娱乐/爱好/读书）、跨时间尺度（长期/短期/重复），
人脑不擅长同时维护"全部待办 + 优先级 + 到期时间 + 精力匹配"。
传统 todo 应用的失效点在于：**它只存储，不思考**。

trueassis 的定位不是 todo list，而是**秘书**：

| 能力 | todo 应用 | trueassis |
|---|---|---|
| 存储事项 | ✅ | ✅ |
| 主动回答"现在该干什么" | ❌ | ✅ `brief` / `next` |
| 结合精力/可用时间/场景筛选 | ❌ | ✅ |
| 让无 ddl 的长期事项不腐烂 | ❌ | ✅ 停滞检测 |
| 从取消理由中学习偏好 | ❌ | ✅ 画像 |
| 自动生成日报/周报 | ❌ | ✅ `journal` |
| 可被任意 AI Agent 直接操作 | ❌ | ✅ 纯文本 + CLI |

## 2. 核心设计原则

1. **纯文本优先（Plain Text as Database）**
   一切是 Markdown + YAML front-matter。可 git diff、可全文搜索、可被任何 LLM 直接读懂、
   二十年后仍然打得开。不用数据库，不用私有格式。

2. **CLI 是唯一写入口，但不是唯一读入口**
   写入走 `assis` 保证字段合法与时间戳正确；读取时 Agent 可以直接 `cat`/`grep` 文件，
   也可以 `assis list --json`。**降级路径永远存在**：即使 Python 挂了，你还能手改 md。

3. **框架与数据分离**
   框架（协议/文档/模版/工具）可公开、可复用、可推远端；个人数据留本地。
   这让"这个系统"和"我的数据"能独立演进，也让别人可以复用框架而不看到你的隐私。

4. **Agent 友好优先于人机交互华丽**
   所有命令支持 `--json`；所有约束写在 `AGENTS.md` 而非代码注释里；
   `doctor` 让 Agent 能自检自己造成的破坏。

5. **只追加，不销毁**
   完成/取消是状态流转 + 归档，不是删除。历史是画像的训练数据。

6. **鼓励放弃**
   `cancel` 必须给理由，但取消本身被系统视为**正向行为**。
   一个不能优雅放弃的系统，最终会变成负债清单，让人不敢打开。

## 3. 概念模型

```
                       ┌─────────────┐
                       │   profile   │  画像：建议的依据来源
                       └──────┬──────┘
                              │ 影响建议
                              ▼
┌──────────┐  实例化   ┌─────────────┐  归档   ┌──────────┐
│ recurring├─────────►│    task     ├────────►│ archive  │
│  (定义)  │ recur run │  (待办实例) │ done/   │ done/    │
└──────────┘           └──────┬──────┘ cancel │ cancelled│
                              │ 归属          └──────────┘
┌──────────┐  拆解      ┌──────▼──────┐
│ project  ├──────────►│  子 task    │
│ (长期)   │            └─────────────┘
└──────────┘
┌──────────┐  提上来    ┌─────────────┐
│  idea    ├──────────►│    task     │
│(someday) │            └─────────────┘
└──────────┘
┌──────────┐
│  event   │  有固定时间点（会议/电影场次/出发）
└──────────┘

        logs（分领域流水）──┐
                            ├──► journal daily/weekly/monthly（自动聚合）
        done/cancelled ─────┘
```

### 五种 kind 的职责边界

| kind | 是否直接"做" | 存放位置 | 特点 |
|---|---|---|---|
| `task` | ✅ | `tasks/active/` | 可完成的具体事项，是执行的基本单位 |
| `project` | ❌ | `projects/` | 通过子任务推进；无可执行子任务时 brief 会告警 |
| `recurring` | ❌ | `recurring/` | 模具，由 `recur run` 生成 task 实例 |
| `event` | ✅ | `tasks/active/` | 有硬时间点，靠 `remind_before` 提前预警 |
| `idea` | ❌ | `tasks/someday/` | 愿望池；不进建议主流，避免噪音 |

**关键取舍**：`someday` 与 `active` 严格隔离。
这是让系统长期可用的核心 —— 如果"想看的电影"和"今天要交的代码"混在一个列表里，
列表就会变成噪音源，人就会停止打开它。

## 4. 状态机

```
   ┌──────────────────────────────────────────────┐
   │                                              │
inbox ──► next ──► active ──► done                │
   │        │        │                            │
   │        │        └──► blocked ──► active      │
   │        │                                     │
   └────────┴────────────────► cancelled ◄────────┘
                (必须给 reason)

  next/active ──► idea (someday)   降级：assis someday <id>
  任意状态 + defer 日期            暂时隐藏，不出现在建议中
```

| 状态 | 含义 | 是否进入建议 |
|---|---|---|
| `inbox` | 刚收集，未澄清（缺 ddl/优先级） | ✅ 但会被提醒去澄清 |
| `next` | 已澄清，排队中 | ✅ |
| `active` | 正在进行 | ✅ 且加分（宜收尾） |
| `blocked` | 被外部依赖阻塞 | ❌ 但会在 brief 单列 |
| `done` | 完成 | ❌ |
| `cancelled` | 放弃（有理由） | ❌ |

`defer` 字段独立于状态：未到 defer 日期的条目不出现在建议中，但仍在系统内。
这实现了"我知道有这件事，但现在别烦我"。

## 5. 建议算法（brief / next 的排序逻辑）

```
score(item) =
    紧急度分   逾期 100 / 今天 80 / 提醒窗口内 45 / 其它 10
  + 优先级分   P0 40 / P1 25 / P2 10 / P3 0
  + 12  如果 status == active         （已开工的先收尾，减少上下文切换）
  + 5   如果属于某个 project           （有杠杆的事优于孤立杂事）
  + 8   如果停滞 ≥ 14 天               （快腐烂了，扶一把）
  + 6   如果预计 ≤ 30 分钟             （短任务容易起步，打破拖延）
```

`next` 命令在打分前先做**硬过滤**：

- `--energy low` → 只保留 energy ≤ low 的任务（不在低谷时段推深度工作）
- `--time 30` → 只保留预计 ≤ 30 分钟的任务（碎片时间不开大工程）
- `--context phone` → 只保留匹配场景或标记 `anywhere` 的任务

这是本系统与普通 todo 最大的区别：**建议要匹配当下的真实状态，而不是只按优先级排序**。
一个 P0 但需要 3 小时深度专注的任务，在你只有 20 分钟且没精神的时候，是个错误建议。

## 6. 反腐烂机制

无 ddl 的事项最容易死掉。系统用三层机制对抗：

1. **停滞检测**：`active` 且 `updated` 超过 14 天 → 进 brief 的「停滞」区，
   并给出三选一动作：推进一步 / 降级 someday / 直接取消。
2. **项目空转检测**：project 名下没有任何可执行子任务 → brief 明确点名。
   这防止"我有个大项目"变成一句空话。
3. **愿望池复盘提醒**：someday 项超过 30 天未复盘 → 提醒批量过一遍。

配套的心态设计：系统**不惩罚放弃**。`cancel` 的输出会明确说
"取消是健康的"，并把理由存下来喂给画像。

## 7. 画像如何影响建议

`private/profile/profile.md` 是人类可读、Agent 可读的自由文本，不做结构化 —— 
因为 LLM 读自由文本比读 schema 更擅长做权衡判断。

它提供三类信息：

| 类型 | 例子 | 影响 |
|---|---|---|
| 节律 | "09:00-12:00 深度工作最佳" | 上午推 high energy 任务，下午推杂事 |
| 偏好/雷区 | "讨厌一天里频繁切换领域" | 建议时倾向同领域连做 |
| 当期重心（≤3） | "本季度重点是金融数据平台" | 重心内的任务额外加权 |

更新是**追加式**的：Agent 把观察写进「近期观察」并注明日期，
不静默重写历史结论 —— 因为"我以前是怎么想的"本身有价值。

## 8. 为什么零依赖

`tools/assis` 只用 Python 标准库（含手写的 YAML front-matter 子集解析器）。
原因：这个仓库要被**任意 AI 工具在任意机器上**直接上手操作。
如果需要 `pip install pyyaml`，那么每个新 Agent 的第一步都是环境排障，而不是干活。

代价是 YAML 只支持子集（标量、内联列表、短横线列表），这对本 schema 完全够用。
`doctor` 会兜住格式错误。

## 9. 有意不做的事（Non-goals）

- **不做 GUI / Web 界面**：入口是 AI 对话与 CLI，不是又一个要打开的 App。
- **不做精确到分钟的日程排程**：日历工具已经做得很好；这里管的是"做什么"，不是"几点几分"。
- **不做多人协作**：单人系统。协作靠现有工具（issue / 项目管理平台）。
- **不做自动决策**：系统只建议，永远由人认领。不自动改优先级、不自动取消。
- **不做云同步服务**：同步用 git（见 `sync.md`），不引入第三方后端。
